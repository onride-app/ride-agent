# Ride workflow

For conversation output, pass `locale: en` for an English user or `locale: zh` for a Chinese user to `get_preferences`, `recommend_traders`, `browse_traders`, `get_trader_profile`, `get_portfolio`, `recalculate_plan` and `preview_copy_orders`. Show the localized `conversation_display`; archived free-form plan metadata remains unchanged. Language only selects presentation. Browser review pages remain English.

If an older client schema has no `locale` parameter, select exactly one `conversation_display.markdown_by_locale.en` or `.zh` matching the user's language. Never print both variants, and do not reconnect or reauthenticate merely to choose presentation language.

Read an exact saved `plan_id` with `get_portfolio` for current `source_evidence` and `order_precheck`, or call the read-only `preview_copy_orders` directly. These reads preserve that plan, preferences, selected traders, allocations, risk settings and expiry. An expired plan can be inspected as saved; inspection does not refresh it or authorize execution. The inspection assumes a flat starting account and current public source snapshots. It does not bind an account, register/configure authority, confirm, fund, run a monitor tick or submit orders. Fixed mode needs verified future opening fills; an incomplete account mode or DEX scope stays unverified.

Distinguish three leverage facts: the legacy Candidate `venue_max_leverage` is the product planning envelope, current per-asset exchange limits are in `source_evidence.market.max_leverages`, and verified source positions report their venue leverage setting. This setting is distinct from current base-Perps notional/equity exposure multiples, which are returned separately only when the scope, equity and timestamps are fully verified. Current positions are not a history of opening trades. `source_equity_usdc: null` before inspection means not inspected, not that the platform has no data. Use source account mode, equity basis, coverage and observation time before interpreting a number. Targets are rounded, netted and checked using the existing risk/order rules; never increase funds, size or leverage to make a preview pass. Allocated collateral is not order notional. Copyability is a model score, not measured fill coverage or a success-rate guarantee. Owned `diagnose_copy` receipts/decisions can provide windowed evidence, but do not invent source/follower matching, slippage or success-rate statistics when coverage and pairing are unverified. Keep default replies to one concise table and a short rule/exit statement; summarize an actual precheck blocker in one sentence. Internal field audits belong in explicitly requested details.

After confirmation, read the same proposal and owned portfolio. `queued`, an active configuration, or a preflight balance does not prove copying is operational. Report `account_bound`, `operational`, `activation.readiness.blockers`, initialized sleeves, source observation times, actual executions and fills separately. An unbound account or blocked activation must not be described as operational. Explain stable blocker reasons in the user's language; unfinished transfers/withdrawals are not a request to add funds. Never clear ownership, old funding records or pending work to make a proposal pass. Registration checks concern the current network and primary trading wallet; unrelated historical wallets remain separate.

`operational: true` means monitoring is ready; it does not prove an order was placed. Read `execution_status` independently. When its status is `blocked_by_risk`, show its summary and concrete `reason` in the user's language, even if monitoring is operational. In Chinese, explicitly say “因风控暂未下单” and explain the returned reason, including the asset and concentration/limit when provided. This status applies only to the proposed target update; report existing orders, executions and fills separately rather than claiming the account has never traded. Use the returned `conversation_display` for a concise explanation. Do not change risk thresholds, add funds or replace traders to bypass the blocker; missing or legacy status evidence is not proof of either a blocker or a placed order.

Copy-confirmation pages support Google and Apple with one explicit sign-in flow and reuse the same owned proposal after returning. A lost popup link must recover in that window, not regenerate or auto-confirm a proposal. On an uncertain submission, read only the original proposal ID; another explicit click is allowed only after the server verifies that it was not submitted. A queued/completed or unverifiable outcome must never be resubmitted. Funding still follows its dedicated inline signing workflow below. Normal sign-in shows no access-code or raw OAuth scope fields. Browser review surfaces default to English; conversation responses follow the user's language. The legacy `ride` local connection alias remains valid even though the service brand is Rider; do not disconnect or rename a working connection merely to change that alias.

Public source positions are sampled independently every five seconds while subscribed; account and source reads reserve separate capacity with a shared venue cooldown. This is snapshot sampling, not proof of complete trade-by-trade WebSocket coverage. Fixed copying still requires verified fill history. Missing/stale source or account evidence suspends increasing execution and preserves targets; a healthy configuration alone is not execution acceptance.

A complete, fresh source snapshot with zero equity and an empty positions array is a verified flat source, not missing data. It can initialize an empty baseline or clear that source's attributed targets while waiting for a new position. Zero equity never serves as a sizing denominator or creates a nonzero target for that source; nonempty positions still require positive finite source equity. Preserve the selected trader, amount and settings rather than replacing a flat trader or asking the follower to deposit. Fixed-mode fill evidence requirements remain in force.

After a recommendation/recalculation timeout, `PREVIEW_RESULT_UNKNOWN`, or closed transport, first call `get_portfolio` once to recover the saved preview. Do not replay the original request or ask for login unless authentication actually failed. Match the saved plan's creation time, budget, risk, explicit traders and other requested preferences to the interrupted request. Show its returned recommendation/comparison only when they match; do not call an older or different plan a recovered result. If matched but expired, refresh the same plan ID with `recalculate_plan`. If not found, explain that the outcome is still unknown rather than silently generating a replacement. Recovery reads never execute trades.

For novice users, display `final_review.risk_setting_explanation` before confirmation and keep per-trader pause/emergency settings in advanced details. Show `metric_period_labels` with historical figures and `sort_warning` when sorting ROI/drawdown; an unknown period must not look comparable. Use `status_breakdown` to distinguish login, plan validity and incomplete account coverage. `known_available_trading_usdc` is only a verified subtotal; never represent it as full account cash or as approval to copy, and never combine market funds as though automatically transferable. Incomplete balances must not invalidate a ready preview.

Default to the returned `conversation_display.markdown` in the user's language: one compact combined allocation/performance table, a concrete copy-rule summary, the exit trigger and next actions. Do not append repeated analysis, long disclaimers or unrequested plans. Keep missing history, source-period uncertainty and human confirmation requirements visible. For the first analysis request, read the exact `plan_id` with `get_portfolio`, `detail: detailed`, `analysis_depth: summary`: show one conclusion, at most three evidence points and a concise data limitation. Offer further analysis with `analysis_depth: extended` on that same ID. Both levels omit formulas and repeated per-trader controls. Use `include_calculations: true` only when the user explicitly asks how calculation/sizing works; never reconstruct formulas from raw values. Analysis and calculations never create another plan. Collapse with `detail: brief`. All allocation/comparison/analysis rows still use the same full selected ID set and order.

“See alternatives”, “看其他 trader” and “more” mean browse candidates, not change trader count. Use `browse_traders` with the saved `plan_id` and `exclude_selected: true`; it omits selected traders and refreshes an expired snapshot when called without a cursor, leaving plans, allocations and preferences intact. Never offer an invented “2-trader alternative” because the budget is small. If the client schema lacks these additive fields, browse with supported fields, clearly omit selected rows when presenting and retain the exact plan; do not substitute a new recommendation. Actual skipped-order evidence can explain a small budget, but never silently changes count or risk.

For an explicit “replace A with B”, use `recalculate_plan` with `plan_id` and `replacements: [{outgoing_trader_id, incoming_trader_id}]`. The server preserves count, each replaced slot's amount, leverage/copy/loss settings and budget/risk preferences, validates fresh eligibility, and returns a new immutable preview. Leave the original plan available. Do not mix replacements with allocations/preferences. Only a separate explicit count/amount/control request uses generic allocations or basket_size; risk-driven system reselection uses the separate base-plan flow below. Older schemas can send the complete original allocation list with just the selected trader IDs replaced; preserve all saved amounts and settings. A request merely to see other traders never authorizes a swap.

When the user changes risk preference on a system-recommended preview and asks for a new recommendation, call `recommend_traders` with `base_plan_id` equal to that exact plan, `selection: system`, and only the requested risk preference patch. Do not merely save a label, recalculate the old fixed members, or ask the user to manually choose replacements for a requested system recommendation. This creates a new preview and preserves the old plan, trader count, slot amounts and copy/leverage/loss controls. User-explicit numerical exit settings remain explicit; a risk label is not permission to change them or increase leverage. This entry requires complete comparable Perps model evidence; `RISK_FIT_UNAVAILABLE` means retain the original plan and report the evidence problem, not reduce count or quietly fall back to an unpersonalized recommendation. Do not force different names: report the versioned risk-selection reasons and actual changes, including a supported unchanged result. The ranking uses normalized same-version model components, not unknown-period ROI/drawdown as though comparable, and does not claim optimal weights or measured risk improvement.

Preserve explicit trader choices. `selection_source: system` identifies automatic recommendations; explicit or legacy-unknown pinned IDs stay protected unless the user explicitly requests system reselection. "Keep these traders; change only the setting" continues to use `recalculate_plan`. Viewing alternatives, explaining a plan, refreshing fixed members, one-for-one replacement and risk-driven system reselection are different operations. For an older schema, a risk-only `recommend_traders` edit of the current last automatic preview (including save-preferences then recommend) is recognized by the server as a slot-preserving system reselect. Use this only when that last owned preview is the intended base and no explicit trader pin must be cleared. Never use it for an older/different target or silently bypass a manual pin. If the exact base, analysis or filters cannot be expressed safely, report the capability limit and refresh tool discovery without changing login or permissions.

`browse_traders.filters` supports `min_score`, `max_drawdown_pct`, `min_roi_pct`, `max_roi_pct`; all percentages are percentage points, not ratios. Apply filters to the complete current verified snapshot before sorting/pagination, and display applied conditions, total matches, excluded missing evidence and source coverage. These are query filters, not saved preferences. A zero threshold is valid; missing values never become zero. Without `metric_window`, describe historical filters as source-reported values and preserve unknown-period labels. An explicit historical period requires exact verified `metric_window: {start_at,end_at}`; unknown/different periods are excluded rather than substituted. Restart without a cursor after changing filters/window/sort; subsequent pages carry the same query. Do not mix exact `compare_ids` with filters/window because named traders cannot be silently removed. A filtered empty result never regenerates the plan, changes count or means funding is required. Production Perps coverage remains the verified top-30 source snapshot, not the whole market.

Identify compared previews using `plan_change.base_plan_id` and `new_plan_id`, their selected IDs and changed count/weights. `alternatives` are one-for-one suggestions based on fewer qualitative overlap flags, not measured risk optimization; an empty list does not prevent browsing other eligible candidates. Show `measured_portfolio_risk_improvement: null` honestly. A two-person subset can raise concentration even if per-trader funding increases; do not label a different plan risk-focused without its own identity and supporting evidence.

Explain `final_review.traders[].copy_rule`, not just the enum “Ride Recommends”. The default Perps rule scales source position quantity by allocated USDC / verified source account equity, with leverage adjustment and any saved multiplier. Fixed mode uses configured margin and verified source fills; proportional mode applies its saved multiplier. Source leverage and venue/user caps, budget/risk, rounding and minimum-order checks apply; undersized entries are skipped, never enlarged automatically. Prediction stays at 1x and follows the corresponding outcome. Do not invent a next order amount without the required current source/equity/venue evidence.

Use the currently available Rider MCP tools and their schemas. The MCP server supplies this workflow through `get_ride_guide`; refresh it at the start of each task. Discover new tools by reconnecting the MCP or starting a new chat. Prefer the connected MCP; when using standalone CLI, read its `--help` and use the equivalent commands. Existing successful login does not require setup or reauthorization after a workflow update. A read-only deployment may expose only a subset; use only available capabilities.

Start recommendations in native AI conversation, not a Widget or complex form. Call `get_preferences` and ask only its missing questions: USDC budget and risk preference (conservative/low, balanced/medium, aggressive/high). Preserve explicit choices. New Agent Perps plans accept positive USDC allocations, including a total budget of 20 USDC; there is no 50-USDC Perps product allocation floor. Allocated collateral is not order notional. Each net opening order is checked after quantity rounding against the current asset-specific venue minimum and checked again before signing at the rounded order price. Orders below that minimum are skipped with a recorded reason; never increase size or leverage to meet it. Missing venue rules block new risk, while venue-permitted reduce-only dust closes remain available. Small budgets may therefore produce a preview but no qualifying entries. Prediction retains its existing allocation minimum of 50 USDC per trader (or a higher venue minimum). Legacy App APIs and existing approved plan settings are unchanged. Never silently shrink an explicitly requested count or increase budget/risk to force a plan.

Risk preference is separate from numeric triggers. Ride planning preset v1 suggests portfolio exit triggers of 10%/20%/30% for low/medium/high when no explicit numeric value exists. These are editable product presets, not a user-approved loss limit, optimized investment advice or a guarantee. `preference_collection.sources` and `suggestions` distinguish user answers from defaults and recommendations. Preserve explicit numeric settings, especially approved or running legacy portfolios. Suggestions become execution settings only through the final frozen proposal and human Ride confirmation. Portfolio exit triggers are separate from each trader's exit/pause thresholds. New Perps Ride-recommended plans follow verified source leverage with no extra user cap by default; an optional custom cap uses the App's editable 1–40x range. A suggested value is not a maximum the user must accept. Use `recalculate_plan` or `update_copy` for an explicit cap change, followed by human confirmation. Actual leverage is the minimum of source leverage, the optional approved user cap and the live per-asset venue limit. Budget, margin, loss triggers, entry checks and actual order minimums still apply; never raise leverage or size just to meet a minimum. Preserve existing approved caps unless explicitly changed. Prediction stays at 1x. Represent no extra user cap as `leverage_cap: null`, never an arbitrary large number. Exchange limits still apply.
