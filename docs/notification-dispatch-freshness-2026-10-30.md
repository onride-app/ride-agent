# 通知积压与账户快照调度

2026-10-30。Core 读取通道上线后的原组合自然窗口完整运行约 490 秒，99/99 样本有效，但快照新鲜度仍失败：一个原组合没有新快照，另一个组合虽有 30 次新快照，仍出现超过 30 秒的停顿。读取通道的成功与原组合连续恢复分别记录。

## 已确认的阻塞

原 runner 在同一用户的 `durable_notify` 事务内串行发送所有到期通知。生产脱敏阶段记录出现约 316 秒的通知尾部；真实 PostgreSQL 回归也确认，通知被阻塞时仍持有用户行锁，另一状态写入得到 `55P03`。生产事务最终失败的具体 SQL 原因尚未由该日志证明。

通知投递现移到独立 dispatcher。金融执行、原 execution ID 对账和日报事件生成仍沿用原有事务和顺序。通知只在提交后排队，外部 HTTP 不持有用户状态行锁，也不延长同用户的账户审计任务。

## 持久化和边界

- 全局最多两个通知 flight，同用户最多一个，按队列轮转。每批最多四条，共用原 20 秒通知期限；不自动紧循环排空全部积压。
- Runner 在原有金融执行与对账逻辑之后，将通知 claim 和已完成结果的 CAS 合并到原 C 事务，登记原事件 ID 和 60 秒租约，不再增加用户 JSON 行锁事务。提交成功后才启动发送；回滚不发送未提交任务，并保留暂存结果和释放预留槽位。
- 发送结果可等下一次 C 提交持久化，只有仍为 pending 且租约 token 匹配的事件才能更新。进程崩溃由原租约和设备回执恢复；未知、超时和关闭保持待重试。旧响应不能复活 cancelled 事件或覆盖新租约。
- 不存在到期通知时不新增通知事务。独立 dispatcher 的备用接口仍支持批量短 claim/ack；Runner 使用合并模式。FIFO 等待者有到期清理，结果缓冲有 2000 用户上限，租约仅为内部状态，不进入用户报告。
- 通知专用截止时间和取消贯穿 adapter、桥接、token 读取、OAuth 与 FCM；金融 RPC 的默认时限和取消规则不变。
- 新增独立 `ride_agent_notification_receipts` 表，只保留用户、事件、不可变内容指纹和设备摘要。空设备摘要是指纹 guard，不能证明送达；只有 FCM 返回结构合法、所属 project 匹配的成功 Message 后，设备记录才可被跳过。原始 token 和通知正文不入此表。
- 多设备投递超时后，重试继续处理尚未确认的设备。全部当前设备都有成功证据时才完成整个事件；相同事件 ID 改变正文、类型或组合归属会拒绝，不能复用旧回执误标成功。

新增表为追加迁移，不改金融 outbox 或原组合配置。旧调用可省略通知截止时间；未完成投递仍走错误与重试路径。App 的事件 ID、通知内容和既有接口保持兼容，此变更不需要 App 或 npm 发布。

## 验证要求

本地回归分别验证数据库行锁、blocked notify 下的后续账户审计、千条失败积压、公平与批量上限、租约排他与恢复、旧回执、撤销、未知结果、设备投递进度和真实 HTTP 取消。部署后仍须对两个原组合重新运行完整自然窗口，保留所有失败和冷启动样本，不能用单次刷新或读取 HTTP 成功代替严格 30 秒验收。真实跟单成交须另有执行证据；本次测试与验收不授权签名、下单、转账或修改真实组合。
